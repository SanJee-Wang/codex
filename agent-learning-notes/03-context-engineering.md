# 模块 C · 从一次对话理解上下文与压缩

> 面向熟悉 Python、暂不熟悉 Rust 的读者。先理解机制，再按文末索引查源码。
> 源码核对基准：本地提交 `27666a63b`，2026-10-27。
> 文中的 Python 都是教学伪代码，不是 Codex 的真实 Python 实现，也不是可直接调用的 SDK 示例。示意数字会单独标明，不代表产品默认配置。

本模块按五个问题展开：

1. 什么是上下文？用户问题、系统指令、AGENTS.md、记忆如何进入模型输入？
2. 用户发出一次请求后，内部发生了什么？上下文为什么会越来越长？
3. 什么情况下会触发压缩？
4. Codex 怎样压缩？总结什么，保留什么，丢弃什么？
5. 压缩会不会丢失关键信息？工程上怎样降低风险？

贯穿案例：**你让 Codex 修复一个 Python 项目的登录接口：登录成功后返回 500；项目要求不能添加新依赖。**

---

## 1. 什么是上下文？先看模型回答之前收到了什么

### 1.1 上下文中有哪些内容？

除了当前用户问题，Codex 还会根据配置、运行环境与执行进度，组织下面这些输入。**它们不一定各自对应一条独立消息：有些会合并，有些通过独立请求字段提供，有些按需读取后才进入上下文。**

这里的「外部记忆」专指跨任务保存的用户画像、偏好和经验，不是当前聊天里的历史消息。

| 输入组成 | 具体包含什么 | 什么时候进入 | Python 示意中的位置或角色 |
|---|---|---|---|
| 基础指令 | 模型的基础工作要求 | 构建模型请求时提供 | `base_instructions`；不要强行当成一条普通历史消息 |
| 开发者指令 | 工作方式、行为要求、输出要求等 | 构建初始上下文及需要更新时 | `role="developer"` |
| AGENTS.md | 用户级、项目级的适用指令 | 初始加载，后续沿用；需要时更新或恢复 | `role="user"`，示意类别 `project_rules` |
| 外部记忆摘要 | 用户画像、偏好、经验、历史信息索引 | 启用记忆功能且存在有效摘要时注入 | 当前记忆扩展通过 developer 上下文提供 |
| 记忆使用说明 | 什么时候使用记忆、怎样找到详细记录、怎样核实旧信息 | 与记忆摘要一起提供 | `role="developer"`；可能和摘要合并 |
| 环境信息 | 当前目录、shell、日期、可用执行环境等 | 根据运行环境及配置提供 | 常见为用户上下文片段，示意类别 `environment` |
| 权限信息 | 文件访问范围、命令执行与审批规则等 | 根据当前权限配置提供或更新 | 权限指令通过 developer 上下文提供；部分环境数据也包含权限信息 |
| Skills 目录及使用规则 | 可用技能的名称、说明、位置、使用要求 | 启用相应机制时提供；完整技能内容另行加载 | 目录指令为 `role="developer"` |
| 工具定义 | 工具名称、用途、参数结构 | 随请求提供，或通过工具发现机制加载 | 独立的 `tools` 字段或专门的工具发现内容，不必是普通消息 |
| 插件、应用相关说明 | 可用能力及其使用方式 | 按启用状态和配置提供 | 相关使用说明可进入 developer 上下文 |
| 工作模式与任务状态 | 计划模式、多 Agent 模式，以及相关功能提供的状态 | 相应功能启用或状态变化时 | 模式指令可为 developer 消息；具体任务状态取决于提供它的功能 |
| 本轮附带内容 | 选中的代码、图片、附件、界面传入的引用等 | 随本轮输入提供 | 可附在用户输入中；图片等使用相应内容结构 |
| 用户当前问题 | 「修复登录成功后返回 500 的问题」 | 接收本轮输入时 | `role="user"`，示意类别 `user_input` |
| 执行过程中获得的信息 | 读到的代码、日志、搜索结果、记忆详情、工具返回值 | 工具执行后进入后续输入 | 与调用对应的工具结果；下面用 `role="tool"` 示意 |
| 之前的历史 | 用户消息、助手输出、工具调用及结果 | 后续调用沿用保留的历史 | user、assistant 及工具调用／结果项 |
| 压缩摘要 | 对旧历史的交接说明 | 已发生相应压缩时，作为替代历史的一部分 | 本文 local 文本摘要路径编码为 user 上下文片段 |

这些项目不是每次无条件全部加载，也不是每轮按此表重新追加一遍。环境、权限、模式、插件等有对应的配置条件；外部记忆也不是必定存在。

**先看初始上下文如何表示。** 下面统一使用 `role`、`kind`、`text` 展示含义：`kind` 是为了阅读而添加的分类标签，`text` 简化了实际消息内容结构，`messages` 也不是这里承诺的真实 API 字段名。条件分支仅表达「按需提供」，不是逐行复刻 Codex。

```python
# 构建初始上下文；后续请求沿用历史，不是每轮重复执行。
messages = [
    {"role": "developer", "kind": "application_rules",
     "text": "说明实际完成的修改和验证结果。"},

    {"role": "user", "kind": "project_rules",
     "text": "AGENTS.md：不能添加新依赖。"},

    {"role": "user", "kind": "environment",
     "text": "当前目录：/project/backend；shell：zsh。"},

    {"role": "developer", "kind": "permissions",
     "text": "本示例只允许在指定工作目录内修改文件。"},
]

if memory_enabled and memory_summary:
    messages.extend([
        {"role": "developer", "kind": "memory_usage",
         "text": "结合历史偏好处理任务；需要具体证据时再读取详细记忆。"},
        {"role": "developer", "kind": "memory_summary",
         "text": memory_summary},  # 假设已保存：用户熟悉 Python，偏好具体机制讲解
    ])

if skills_catalog_enabled:
    messages.append({
        "role": "developer", "kind": "skills_catalog",
        "text": "可用技能及其说明、路径、使用规则：……",
    })

if app_or_plugin_instructions_enabled:
    messages.append({
        "role": "developer", "kind": "app_plugin_instructions",
        "text": "当前启用的应用、插件能力与使用要求：……",
    })

if mode_instructions_enabled:
    messages.append({
        "role": "developer", "kind": "mode_instructions",
        "text": current_mode_instructions,  # 例如当前计划模式的行为约束
    })
```

实际实现可能把多个 developer 片段合成一条消息，其他部分也可能按不同位置排列。因此，不要从这段示例推导出固定消息条数或精确顺序。

外部记忆这里也有明确实现：当前记忆扩展读取 `memory_summary.md`，将摘要与记忆使用说明组织为 developer 上下文。**详细记忆不是因此全部加载**，需要时再通过读取或检索进入后续输入。实际是否启用，仍取决于配置。

**再看本轮问题和附带内容。** 在已有上下文基础上，加入本轮输入；文本选区可以这样示意，图片和其他附件则需要相应内容结构：

```python
if selected_code:
    messages.append({
        "role": "user", "kind": "selected_code",
        "text": selected_code,
    })

messages.append({
    "role": "user", "kind": "user_input",
    "text": "修复登录成功后返回 500 的问题。",
})

request = {
    "base_instructions": "你负责协助用户完成开发任务。",
    "messages": prepare_for_model(messages),
    "tools": [read_file_definition, run_tests_definition],
}
```

所以，基础指令和工具定义也属于模型的输入，但**不能因此认为所有输入都必须被包装成 user 消息，或全部塞在 `messages` 里面**。

**进入执行过程以后，还会增加助手输出、调用与工具结果。** 下面沿用常见的 assistant/tool 写法帮助理解，真实 Codex 可以使用专门的调用和输出类型：

```python
messages.extend([
    {"role": "assistant", "kind": "tool_call",
     "call_id": "call_1", "name": "read_file",
     "arguments": {"path": "auth/login.py"}},
    {"role": "tool", "kind": "tool_result",
     "call_id": "call_1", "text": login_file_contents},
])
```

读取详细记忆、完整技能说明或其他项目文件后，返回内容也可通过这条工具结果路径进入上下文。工具结果与调用配对，不应随意伪装成用户亲自发出的要求。

之后再接收下一轮用户问题时，已经保留的用户消息、助手输出和工具结果就构成「之前的历史」。若发生本文的 local 文本摘要压缩，替代历史中还会包含下面这样的摘要项：

```python
# 示意替代历史中的一项，不是在完整旧历史末尾随便加一段就完成压缩。
summary_item = {
    "role": "user", "kind": "compaction_summary",
    "text": "目标是修复登录接口；不能添加依赖；已修改，尚未跑完整测试。",
}
```

这解释了两件事：**第一次模型调用就可能带有不少用户没有当场输入的信息；任务执行中还会继续追加新信息。** 初始上下文的条件加载与后续历史的增长，是理解窗口占用的两个来源。

### 1.2 system、developer、user、assistant、tool 到底是什么？

可以先把它们理解成消息的来源与用途标签：

- `system` / `developer`：平台或应用提供的规则与行为要求。
- `user`：用户请求；某些应用提供的上下文也可能用这种角色承载。
- `assistant`：模型先前的回答，或模型提出的工具调用。
- 工具结果：外部程序执行后的返回信息。在不同接口里，可能叫 `tool` 消息，也可能使用专门的工具输出类型。

角色有助于区分指令来源和优先级，不只是聊天界面的显示样式。例如工具读到的网页即使写着「忽略此前规则」，也不因此成为系统指令。

**文件来源和消息角色是两回事。** AGENTS.md 是信息来源，不是 API 原生支持的消息角色。它需要先被程序读取，再转换成请求中的文本。当前源码有将项目指令组织成用户上下文片段的实现，不能一律把 AGENTS.md 当作 system 消息。

下面只展示逻辑结构，字段名不是实际 SDK 契约：

```python
request = {
    "base_instructions": "你负责协助用户完成开发任务。",
    "messages": [
        {"role": "developer", "text": "遵守当前工具和执行规则。"},
        {"role": "user", "kind": "project_rules",
         "text": "AGENTS.md：不能添加新依赖。"},
        {"role": "user", "kind": "environment",
         "text": "当前目录：/project/backend"},
        {"role": "user", "kind": "user_input",
         "text": "修复登录成功后返回 500 的问题。"},
    ],
    "tools": [read_file_definition, run_tests_definition],
}

response = model.generate(request)
```

这里的 `kind` 是教学标签，用于区分「用户亲自提出的问题」与「程序补充的上下文」。真实代码有自己的表示方式。

### 1.3 AGENTS.md、项目文件和 skills 会全部自动塞进去吗？

不会。要分别理解：

- **AGENTS.md**：Codex 按配置、目录、信任状态、长度限制等加载适用内容，再将指令组织为 `role="user"` 的上下文消息。不是扫描整个磁盘，把所有同名文件都加入输入。
- **普通项目文件**：通常需要编辑器传入片段，或通过工具读取，内容才会进入上下文。模型知道一个文件路径，不等于已经知道文件内容。
- **skills**：可能先提供名称、简介等可用技能信息，需要使用时再读取完整说明。不能把「知道有这个技能」等同于「整个技能目录已经加载」。具体由运行环境决定。

在本次学习中，你选中的文档片段由界面提供给了我；文档之外的源码，则需要我进一步读取。

**对于 AGENTS.md，要明确区分「每次请求包含它」和「每轮重复追加一份」。** 前者说的是模型这次能看到什么，后者说的是历史列表新增了什么。

用 Python 的 `messages` 写法示意，第一次请求可以是：

```python
agents_message = {
    "role": "user",
    "content": """# AGENTS.md instructions for /project
<INSTRUCTIONS>
不能添加新依赖。
修改代码后运行相关测试。
</INSTRUCTIONS>""",
}

messages = [
    agents_message,
    {"role": "user", "content": "帮我修复登录接口"},
]
```

`user` 是 `role` 字段的值，文档文本放在消息内容里；它不是一个名为 `user` 的内容字段。

在尚未压缩、指令未变化的简化情况下，后续请求继续使用历史里的这份指令：

```python
messages = [
    agents_message,  # 原来就在历史里，后续请求继续包含它
    {"role": "user", "content": "帮我修复登录接口"},
    {"role": "assistant", "content": "已经修改，登录测试通过。"},
    {"role": "user", "content": "再检查一下异常处理"},
]

# 不需要每轮再执行 messages.append(agents_message)。
```

这两个列表是先后两次请求的示意快照，不是要求把第一份历史重新追加到第二份历史里。基础指令、工具交互等在这里省略；真实请求也不一定使用名为 `messages` 的字段。

| 容易混淆的说法 | 准确理解 |
|---|---|
| 每次请求都包含 AGENTS.md | 在正常任务推理、指令仍适用的情况下，模型通过保留或恢复的上下文继续获得它；不代表每次都新增消息 |
| 每轮重复追加相同 AGENTS.md | 当前实现不会这样处理；已提供的指令状态未变化时，不生成新的更新消息 |
| 每次调用模型都重新读磁盘 | 不一定；加载有缓存和刷新规则，不能由「请求包含它」推导出「每次都读文件」 |
| 指令状态变化后怎么办 | 检测到变化时，生成相应的替换或移除通知；这不等于磁盘编辑一定即时生效 |
| 压缩移除了旧上下文后怎么办 | 按压缩阶段恢复必要上下文；本文 local 路径在 mid-turn 立即注入，pre-turn／手动压缩则在下一次常规 turn 完整恢复 |

因此，「每次请求包含它」应理解为**逻辑上仍提供适用的指令**，不能扩展成「所有类型的模型调用都逐字包含同一份文件」，也不表示网络传输每次都完整重发。状态未变化时不重复追加，也不意味着它不再占用模型上下文空间。

### 1.4 外部记忆：自动注入的概览与按需读取的详情

这里的记忆专指**跨任务保存在模型之外的用户画像、偏好、历史决策与项目经验**。例如，系统从以往任务中整理出「用户熟悉 Python」「偏好直接解释机制」「某个项目曾经采用过某种方案」。本节关注这些信息怎样进入一次模型请求，暂不展开记忆生成与更新流程。

从输入装配的角度，可以分成两层。它们不是只有两个文件，而是承担两种不同作用：

| 层次 | 保存什么 | 怎样进入上下文 |
|---|---|---|
| 自动注入的概览 | 简短的用户画像、偏好、通用经验，以及详细记忆的索引或线索 | 记忆功能启用且摘要有效时，由程序读取，与记忆使用说明一起加入 developer 上下文 |
| 按需读取的详细记忆 | 项目历史、决策背景、具体操作经验、任务摘要和证据引用等 | 模型判断需要细节后，请求搜索或读取；返回内容通过工具结果进入后续输入 |

**第一层让模型先知道可用的背景和线索，第二层在需要时补足证据与细节。** 不是每来一个问题，都固定检索全部记忆并拼接进去。

#### 第一层：程序自动提供记忆概览

当前源码会从对应版本的记忆目录读取 `memory_summary.md`。记忆整合模板包含用户画像、用户偏好、通用经验、记忆索引等栏目。

假设系统已经保存了下面这些信息，摘要可以是：

```text
用户画像：熟悉 Python，正在学习 AI Agent 的工程实现。
用户偏好：重点解释具体机制；不重复讲解已经掌握的基础概念。
历史线索：此前讨论过登录服务的异常处理，详情见某条任务摘要。
```

这是内容示例，不表示这些信息已经写入当前用户的持久化记忆。当前聊天里知道某个偏好，也不能据此断言新聊天一定能获取它。

自动注入有条件：当前实现要求记忆功能开关与使用配置开启，并且能读到非空摘要。源码中这份摘要的截断预算常量是 2,500 token，使用近似 token 处理；这个限制针对摘要文本，不包括外面的记忆使用说明，也不是所有详细记忆的总容量。

用 Python 伪代码表示这段装配：

```python
# 构建完整上下文时的一个组成步骤，不是每条用户消息都重复追加。
if memory_feature_enabled and use_memories:
    summary = read_optional_text(memory_root / "memory_summary.md")

    if summary and summary.strip():
        summary = truncate_text(summary.strip(), token_budget=2_500)
        messages.append({
            "role": "developer",
            "kind": "memory_context",  # 教学分类，不是真实 API 字段
            "text": render_memory_template(
                usage_rules=memory_usage_rules,
                summary=summary,
                memory_root=memory_root,
            ),
        })
```

因此，模型在执行第一次工具调用之前，就可能已经知道某些历史偏好和可用记忆的位置。它不必先读取所有历史记录，才能知道这些概览信息。

**为什么使用 developer 角色？** 当前实现将「应用规定的记忆使用方式」与「作为历史背景的摘要」一起包装为 developer 上下文。前者规定如何读取、核实、使用记忆；后者不是一组天然高于当前用户要求的绝对命令。

例如，历史摘要说「通常喜欢 Python 示例」，用户当前要求「这次使用 Rust」，不应把历史偏好当作必须拒绝当前要求的理由。当前 V2 记忆模板明确要求把摘要当作历史上下文、遵循当前指令，并且不能把记忆当成当前事实的证明。

#### 第二层：确实需要时，再读取详细记忆

概览未必包含完整的决策过程、原始措辞或验证证据。如果用户问「之前为什么选择这个异常处理方案」，只知道「以前讨论过」就不够，需要进一步获取当时的记录。

当前记忆模板存在版本差异：V1 引导模型从 `MEMORY.md` 等索引查找相关记录；V2 可以直接利用注入摘要中的具体线索，在额外证据、措辞、时间顺序或不确定性会影响答案时读取对应的任务摘要，缺少必要线索时再搜索。不要把某一种检索顺序说成所有版本的固定流程。

详细内容可以通过记忆专用工具或适用的文件读取、搜索工具获得，具体取决于配置。下面只模拟一次有明确目标的读取：

```python
# 模型已看过概览，并决定需要核对某次历史决策。
call = {
    "role": "assistant", "kind": "tool_call",
    "call_id": "memory_read_1",
    "name": "read_memory",  # 教学名称，不承诺真实工具名
    "arguments": {"reference": relevant_history_reference},
}
messages.append(call)

detail = execute_tool(call)
messages.append({
    "role": "tool", "kind": "memory_detail",
    "call_id": "memory_read_1", "text": detail,
})

# 下一次推理既能使用原有概览，也能使用刚返回的详细记录。
response = model.generate(
    base_instructions=base_instructions,
    messages=prepare_for_model(messages),
    tools=available_tool_definitions,
)
```

如果概览已经足以处理当前问题，不一定还要读取详情。尤其不能把每次询问都理解成一次自动的向量检索：这里能直接确认的是摘要注入、记忆使用指引，以及按需调用工具获取更多内容。

#### 两层分别怎样占用上下文？

```text
外部存储中的记忆
  ├─ 概览摘要 → 按条件自动注入 → 占用本次上下文
  └─ 详细记录 → 有需要时读取   → 返回的内容才进入后续上下文
```

详细记忆仍在外部存储时，不会仅因为「存在」就全部占据模型窗口。读取后则会增加输入大小，后续也可能参与上下文压缩。

外部记忆摘要与本模块后面介绍的对话压缩摘要也要分开：前者提供跨任务背景，后者主要用于继续当前任务；它们的生成目的、注入方式和预算并不相同。详细记录即使仍保存在磁盘上，模型也需要重新获取，不能靠「已经持久化」保证当前推理掌握所有内容。

本节依据：[记忆扩展的启用条件与 developer 注入](../codex-rs/ext/memories/src/extension.rs)、[概览读取与模板组装](../codex-rs/ext/memories/src/prompts.rs)、[摘要预算常量](../codex-rs/ext/memories/src/lib.rs)、[V1 读取指引](../codex-rs/ext/memories/templates/memories/read_path.md)、[V2 读取指引](../codex-rs/ext/memories/templates/memories/read_path_v2.md)。

## 2. 用户只问了一次，为什么上下文还能不断增长？

### 2.1 一次用户请求，不等于一次模型调用

你发送「修复登录接口」，Codex 可能需要依次读文件、查错误、修改代码、运行测试。每获得新的结果，都可能再次调用模型，让它决定下一步。

我们把处理一次用户请求的执行轮次称为 **turn**。一个 turn 内可以有多次模型调用和工具执行。

```text
你发出请求
  ├─ 模型调用 1：决定读 login.py
  ├─ 工具执行：返回 login.py 内容
  ├─ 模型调用 2：决定运行登录测试
  ├─ 工具执行：返回错误堆栈
  ├─ 模型调用 3：决定修改代码
  ├─ 工具执行：返回修改结果
  ├─ 模型调用 4：决定再次运行测试
  ├─ 工具执行：返回测试结果
  └─ 模型调用 5：向你说明修复结果
```

这是一种示例轨迹，不是固定步骤。关键是：你没有继续发消息，Agent 也能产生新的上下文。

### 2.2 用一个 Python 循环理解它

下面暂时省略压缩、中断、并发和错误重试，只看历史怎样增长：

```python
history = build_initial_context()   # 项目规则、环境等历史项
history.append(user_message("修复登录接口"))

while True:
    response = model.generate(
        base_instructions=base_instructions,
        messages=prepare_for_model(history),
        tools=tool_definitions,
    )
    history.extend(response.items)

    if not response.tool_calls:
        break                      # 教学简化：本轮回答完成

    for call in response.tool_calls:
        result = execute_tool(call)
        history.append(tool_result(call.id, result))
```

重点看 `history.extend(...)` 和 `history.append(...)`：模型输出和工具结果都会继续增加历史。

真实 Agent 还有其他继续或结束条件，不是「没有工具调用」就一定结束。这里先用最小循环说明机制。

`prepare_for_model` 也不是原样复制：它会整理调用与结果的配对，处理模型不支持的图片、音频等内容。这里只需要知道，内部保存的历史在发送前还会经过整理。

### 2.3 后一次推理为什么还需要前面的内容？

模型看到测试错误时，还需要知道：用户想解决什么、项目有哪些约束、错误对应哪段代码，以及刚才试过什么。

如果只提供一句 `TypeError: ...`，它可能不知道这个错误与当前任务的关系。

因此在未压缩、未进行其他裁剪的简化情况下：

```text
第 1 次输入：工作规则 + 项目规则 + 用户问题
第 2 次输入：上述内容 + 读取文件的调用 + 文件内容
第 3 次输入：上述内容 + 测试调用 + 错误堆栈
第 4 次输入：上述内容 + 修改调用 + 修改结果
……
```

「模型能继续记得」依赖本次推理仍可获得这些信息，可能通过保留历史，也可能通过压缩后的摘要。

这里描述逻辑上可用的信息。实际传输可能使用缓存或服务端状态复用，不一定每次在网络上完整重发。**缓存能减少某些重复计算或传输开销，但不能据此认为这些内容不再占模型的上下文容量。**

### 2.4 什么是上下文窗口？token 是什么？

上下文窗口可以先理解成：**模型一次推理能够处理的信息容量上限。** 不要把它想成可以无限扩展的聊天记录数据库。

容量通常用 token 衡量。token 是模型处理文本时使用的单位，并不固定等于一个汉字、一个英文单词或一个字符；代码和自然语言的切分也不同。图片、音频还有相应的容量计量方式。

输入已经占满空间时，还要考虑后续生成所需的容量，因此工程上通常不能把整个理论窗口都当作可自由填满的历史空间。不同模型和接口还可能有独立的输入、输出限制。

在本案例里，占用空间的不只是用户问题：

```text
本次输入占用
≈ 基础和开发者指令
+ 项目规则与环境信息
+ 工具说明
+ 保留的对话历史
+ 文件内容、搜索结果、测试日志
+ 已注入的记忆或旧摘要
```

这是帮助理解的组成关系，不是 Codex 的精确 token 计算公式。

### 2.5 为什么读几个文件就可能占掉很多空间？

用户问题可能只有几十个 token，但一次搜索可能返回大量匹配，一次测试可能输出很长的堆栈，一次读文件可能带回几千行代码。

以下数字完全是假设，仅用于展示增长：

| 时刻 | 当前输入大小 |
|---|---:|
| 加载规则、工具说明和用户问题后 | 8,000 token |
| 读取几个源文件后 | 24,000 token |
| 搜索调用关系后 | 39,000 token |
| 多次测试、读取日志后 | 68,000 token |
| 继续修改并验证后 | 82,000 token |

所以，**窗口不够用并不要求用户聊了很多轮；一个复杂开发任务内部的工具循环就可能让它增长很快。** 单次工具输出截断等措施可以减缓增长，但不能消除长期积累。

## 3. 什么情况下触发压缩？

### 3.1 先区分「窗口容量」与「自动压缩阈值」

窗口容量是模型的能力边界；自动压缩阈值是应用决定何时整理上下文的运行策略。两者不是同一个概念。

假设某个教学系统可用窗口为 100,000 token，将自动压缩阈值设为 80,000 token。当输入接近后者时，就主动整理历史，而不是必须等服务端报错。

**100,000 和 80,000 都是示例数字，不是 Codex 默认值，也不是固定 80% 规则。**

```python
# 简化模型：真实 Codex 会结合使用量、估算值、配置与模型信息。
status = measure_context_usage()

if status.auto_compact_limit_reached or status.usable_window_limit_reached:
    compact_before_continuing()
```

当前源码中的判断涉及自动压缩的计量范围、模型有效上下文上限，以及特定配置下的缓冲区。不能只根据聊天条数判断，也不能把一次累计账单上的 token 总数直接当成当前窗口占用。

这里的「自动压缩计量范围」是指：配置决定用哪部分上下文占用来对照自动压缩预算；无论如何，模型完整窗口仍有独立的上限检查。

### 3.2 在任务的哪些阶段检查？

| 时机 | 用案例理解 | 压缩之后 |
|---|---|---|
| 开始正常推理前（pre-turn） | 前面已经聊了很久，这次准备继续处理登录问题 | 成功后进入本轮正常处理 |
| 执行过程中（mid-turn） | 读代码、跑测试后上下文达到限制，但任务还需要继续 | 成功且未被中止时，继续当前 turn |
| 回答完成后（post-turn） | 已经回答修复结果，满足配置的轮后压缩阈值 | 为后续执行整理历史 |
| 用户手动请求 | 用户主动要求压缩 | 按配置选择实现 |

Pre-turn 不能简单理解成「准确预测加上新消息后一定超限」。当前实现会检查已有 token 状态，也处理部分模型切换相关情况。

### 3.3 达到阈值，是否一定能够继续？

不一定。正常意图是先压缩再继续，但压缩也可能失败：模型请求错误、中断、预算不足、重试耗尽等都会影响结果。

尤其要考虑：**负责生成摘要的模型调用本身也需要容纳输入。** 如果等到历史已经过大才处理，连「请总结这些内容」的请求都可能装不下。

本文后面介绍的文本摘要路径，在压缩请求超窗时会尝试移除最旧历史项后重试；无法恢复时返回错误。移除的内容也可能不再被本次摘要看到。

Mid-turn 压缩失败可能结束当前 turn；post-turn 失败通常不会撤销已经完成的回答。不要把「达到阈值后尝试压缩」说成「任何超限都能无损恢复」。

## 4. Codex 到底怎么压缩？

### 4.1 先明确本节讲的是哪一种实现

先学习最容易理解的**客户端文本摘要路径**：Codex 程序调用模型生成一份交接摘要，再组织新的历史。源码将它称为 local；这里的 local 指客户端编排，**不表示模型一定在本机运行**。

Codex 当前还有 Remote V2 和 TokenBudget 分支。它们与本文主流程的区别放在第 4.8 节，先不让分支细节打断理解。

### 4.2 压缩不是 ZIP，而是写一份交接说明

假设修复任务做到一半，历史里已经有大量源码和日志。让下一个模型继续工作，往往不需要再次逐字阅读所有失败堆栈，但需要知道：

- 用户要解决什么；
- 不能违反什么约束；
- 已经做了什么；
- 哪些结论已验证，哪些仍是假设；
- 下一步该做什么、去哪里获取细节。

一份**示例摘要**可能是：

```text
目标：修复登录成功后返回 500，保持现有响应格式。
约束：不能添加第三方依赖。
已确认：错误发生在响应序列化阶段；相关代码位于 auth/login.py。
已完成：修改了该文件，登录相关测试已通过。
尚未完成：没有运行完整测试集，没有提交或部署。
下一步：检查其他调用方是否受影响，再运行完整测试集。
```

这只是示例，不是刚刚在真实项目中发生的执行记录，也不意味着模型每次都会生成这么完整的摘要。

它与 ZIP 的区别是：**摘要通常不能还原所有原始内容，是有损的语义整理。**

### 4.3 第一步：让模型总结当前历史

不是先把用户消息拿走、只总结助手和工具输出。程序会将当前可用于请求的历史，加上总结指令，交给模型。

```python
summary_request = prepare_for_model(copy(history))
summary_request.append(user_message(
    "为接手任务的模型写交接摘要：包含进度、决策、约束、"
    "用户偏好、待办事项和继续工作所需的关键引用。"
))

summary = model.generate_summary(
    base_instructions=base_instructions,
    messages=summary_request,
)
```

这里的模型能看到用户消息、助手消息、工具交互，以及可能存在的旧摘要；但输入仍受之前的截断、压缩与本次超窗重试影响。

「当前历史」不等于「从会话开始以来的全部原始记录」。程序也不会仅因为磁盘中有旧日志，就自动把它们全部找回来参与总结。

### 4.4 第二步：独立选择要原文保留的用户消息

生成摘要以后，程序还会尽量保留近期用户文本，避免最近需求完全依赖模型转述。

在本次核对的源码版本中，这条路径的用户文本保留预算常量是 **20,000 token**。实际采用近似计数，从新到旧选择，最后恢复时间顺序；这个数值不是永久不变的产品约定。

下面只模拟纯文本用户输入，省略真实消息的附件、注释和元数据：

```python
def select_recent_user_texts(history, budget=20_000):
    # kind 是教学标签：排除项目规则、环境信息和旧摘要。
    user_messages = [m for m in history if m.kind == "user_input"]
    selected = []
    remaining = budget

    for message in reversed(user_messages):
        if remaining <= 0:
            break

        size = estimate_tokens(message.text)
        if size <= remaining:
            selected.append(copy(message))
            remaining -= size
        else:
            text = truncate_middle(message.text, token_budget=remaining)
            selected.append(user_message(text))
            break

    return list(reversed(selected))
```

**20,000 只限制这部分保留的用户文本。** 它不是模型窗口容量，不是自动压缩阈值，也不包括新摘要与重新注入的上下文。

当纯文本消息预算足够时，真实实现保留其内容部分及相关元数据；超预算的一条进行中间截断，然后停止选取更早消息。包含图片、音频等内容时，这条 local 路径会回退到文本，不能承诺多模态消息原样留下。

这里还有一个容易误解的点：**原文保留与总结是两件事，同一条用户要求可以同时出现在保留消息和摘要中。** 早期消息没有被原文保留，也不代表它的语义必然消失；模型可能已经把它写入摘要，但没有绝对保证。

### 4.5 第三步：重建历史，并恢复运行上下文

程序首先组织「选中的用户消息 + 新摘要」。如果是在当前 turn 中途压缩，会立即恢复必要的项目与运行上下文；如果是在 pre-turn 或手动压缩场景，则推迟到下一次常规 turn 完整恢复。

为什么不让模型自己记住权限、当前目录等所有信息？因为运行时已经持有这些信息，而且可能在变化。重新从当前状态构建，比只依赖摘要描述更可靠。这是从实现得到的工程解释，不代表所有状态都有相同的恢复机制。

```python
# 继续模拟 local 路径；省略并发更新、持久化细节与错误分支。
new_history = select_recent_user_texts(history)
new_history.append(summary_message(summary))

if phase == "mid_turn":
    context = rebuild_context_from_current_runtime()
    new_history = insert_before_last_user_or_summary(new_history, context)
else:
    # 这里的 else 仅代表 pre-turn / 手动压缩场景。
    mark_context_for_reinjection_on_next_regular_turn()

history = new_history
save_compaction_checkpoint(history)
refresh_context_usage()
```

基础指令仍由请求的相应字段提供，不能认为所有系统规则都包含在 `new_history` 里。

典型的 mid-turn 布局是：

```text
压缩前：
项目上下文 → 用户要求 1 → 助手/工具交互 → 用户要求 2 → 更多交互

压缩重建后：
保留的用户要求 1 → 重新构建的上下文 → 用户要求 2 → 新摘要

继续执行后：
上述内容 → 新的工具调用 → 新的执行结果 → 新的助手输出
```

把上下文插在最后一条真实用户消息之前，是为了满足该路径的 mid-turn 模型位置约定，让摘要在典型重建结果中位于末尾。没有真实用户消息时使用其他插入位置。

但不能说「摘要永远最后」：后续消息会追加，真实实现还会处理压缩期间新接受的 goal 更新等情况。上面的伪代码没有模拟这些并发状态处理。

### 4.6 到底保留了什么，丢了什么？

以下仍只讨论 local 文本摘要路径。

| 内容 | 压缩后的主要去向 | 是否保证完整 |
|---|---|---|
| 基础指令 | 继续通过模型请求提供 | 不依赖摘要复述，但不要与所有历史指令混为一谈 |
| 可重建的项目与运行上下文 | 按阶段从运行时重新组织 | 以运行时当前提供的内容为准，不保证与最初文本逐字一致 |
| 近期用户文本 | 在近似 20,000 token 预算内保留 | 预算不足会截断；更早消息可能不原文保留 |
| 用户消息中的图片、音频 | 这条重建路径回退到文本 | 不保证媒体本身留下 |
| 助手回答、工具调用和输出 | 主要由新摘要承接信息 | 原始交互通常不再逐条保留于该替代历史 |
| 旧摘要 | 可参与本次总结，再由新摘要替代 | 可能进一步丢失信息 |

「没有保留在模型后续使用的历史里」不等于「已经删除磁盘上的旧记录」。压缩会更新活动历史，并保存带有替代历史的检查点；持久化本身另有筛选规则，也不能反过来承诺所有原始数据都完整落盘。

压缩后想恢复细节，可能需要再次读取源码、重新检索记录或重新运行检查。磁盘中存在这些数据，并不意味着模型自动拥有它们。

### 4.7 压缩之后，为什么还能继续修 Bug？

因为后续推理仍然能得到任务目标、保留下来的用户要求、当前运行上下文，以及摘要里的进度和下一步。模型据此继续请求工具，程序再把新结果加入历史。

但这种连续性依赖摘要质量和可恢复的外部信息。它不是「把模型脑中的全部状态保存下来再加载」，也不是保证行为完全等价的无损变换。

### 4.8 现在再看其他路径，避免把主流程当成唯一实现

| 实现 | 与前面主流程的区别 |
|---|---|
| local 文本摘要 | 本节详细解释的路径：客户端组织摘要模型调用，再按规则重建历史 |
| Remote V2 | 使用另一套远端压缩及历史重建逻辑；当前保留消息预算常量为 64,000 token，保留对象也不只是真实用户文本；客户端代码不能完整揭示服务端算法 |
| TokenBudget 分支 | 启用对应功能时，压缩生命周期中跳过模型/服务端总结，安装新的上下文窗口；不能用前面的摘要流程推导该分支保留哪些信息 |

自动与手动压缩都会根据配置、provider 能力等进行路径选择。面试时应说「以 local 文本摘要路径为例」，不能说「Codex 所有压缩都保留 2 万 token 用户消息」。

## 5. 压缩会不会丢失关键信息？

### 5.1 会，而且「有摘要」不等于「没有遗忘」

local 路径至少存在这些损失来源：

1. 用户文本超过保留预算后被截断或不再原文保留。
2. 模型总结时遗漏信息，或错误概括状态。
3. 工具输出在进入总结前就可能经过截断。
4. 压缩请求超窗后，重试过程可能先移除部分历史。
5. 连续多次压缩，对旧摘要再次概括，损失可能累积。

当前源码也会提醒：长会话和多次压缩可能让模型准确性下降。不能把有损摘要当成可靠的事实数据库。

### 5.2 哪些错误会直接影响业务？

仍然使用登录接口案例：

| 原始事实 | 错误或不充分的摘要 | 可能后果 |
|---|---|---|
| 不允许添加新依赖 | 未记录该约束 | 后续方案引入新包 |
| 仅登录相关测试通过 | 「测试全部通过」 | 没有进行完整验证就声称完成 |
| 已修改，尚未提交或部署 | 「问题已修复上线」 | 用户误判实际交付状态 |
| 错误来源只是初步怀疑 | 「已确认根因」 | 后续排查被错误结论带偏 |
| 某个外部操作已经执行 | 没记录执行结果 | 后续重复执行，产生重复通知或订单等副作用 |

判断信息是否重要，应看它对后续决策的影响，不能只按消息角色判断。工具输出中也可能包含最关键的事实。

### 5.3 怎样降低风险？哪些是机制，哪些是工程建议？

本节已经看到的 Codex 机制包括：优先保留近期用户文本、从运行时重建部分上下文、提示模型保留关键约束和待办、保存压缩检查点。这些措施降低风险，但不保证零丢失。

以下是设计 Agent 时可以借鉴的工程建议，不表示当前 compaction 已经自动实现所有检查：

- **关键业务状态结构化保存**：例如 `patch_applied=True`、`tests_scope="login_only"`、`deployed=False`，不要只依赖自然语言摘要。
- **保留可回查的证据**：文件路径、测试名称、执行记录标识；需要精确判断时再读取原记录。
- **把已验证事实和假设分开**：避免摘要把「可能」改成「确定」。
- **对外部操作使用幂等与状态查询**：不要仅凭模型记忆决定是否再次发送、扣款或创建资源。
- **评估语义保留率**：检查关键约束与状态是否仍正确，而不只是看 token 数减少了多少。

这些方法仍有边界：源码会变化，日志可能不完整，外部状态可能更新。因此重新读取或查询本身也需要考虑时效性。

### 5.4 如果自己实现一个简化版本，怎样验证？

构造一段包含以下事实的历史：

```python
expected_facts = {
    "allow_new_dependencies": False,
    "changed_file": "auth/login.py",
    "tests_scope": "login_only",
    "full_suite_run": False,
    "deployed": False,
}
```

分别验证两类行为：

- **程序规则**：近期用户消息优先；预算不足时截断；旧摘要不被误当作真实用户消息；摘要调用失败时不直接丢掉原历史。
- **摘要质量**：让接手模型根据压缩结果回答「完整测试跑了吗」「部署了吗」「能加依赖吗」，核对是否与事实一致。还要测试第二次、第三次压缩后的结果。

可以把旧事实放在很早的位置、把最新更正放在末尾，检查模型是否正确保留了最终状态。单次通过不代表以后永远正确，应该用多组任务与重复实验评估。
